# API Test Agent

An agent that takes a base URL and a list of API endpoints, probes the real API, uses Claude to plan and write API tests in Playwright or Pactum (Mocha), runs them, reports suspected API bugs, and exports a standalone test framework. Endpoints can also be imported from OpenAPI, Postman, cURL, HAR or ticket text. API Test Agent is a SprintSynergy product under active development. Repo: `sprintsynergyio/api-test-agent` (the local folder name may differ). Status and plan: `docs/ROADMAP.md`; setup: `docs/TEAM-SETUP.md`; demo guide: `docs/DEMO.md`.

## Model providers (`agent/claude.ts`)

The model is chosen once per process from the environment (`modelChoice()`), printed as `model: <provider> <model> (API key|Claude Code login)` after the framework line, and written to `summary.model { provider, model, via }`.

| `.env` | Path |
|---|---|
| `LLM_PROVIDER` unset or `anthropic`, no `ANTHROPIC_API_KEY` | the Claude Code CLI in headless mode (`claude -p`) with the machine's login (`via: "cli"`) |
| `anthropic` with `ANTHROPIC_API_KEY` | the Messages API over HTTPS, billed to the key; default model `claude-sonnet-5-5` |
| `LLM_PROVIDER=openai` with `OPENAI_API_KEY` | the Chat Completions API (`max_completion_tokens`, system plus user message); default model `gpt-6.1-sol` (OpenAI's balanced model as of Nov 2026). Without the key the run stops before probing with `LLM_PROVIDER=openai requires OPENAI_API_KEY` |

`LLM_MODEL` overrides the model for either provider; `CLAUDE_MODEL` still works as the old name for the Anthropic model. `ANTHROPIC_BASE_URL` and `OPENAI_BASE_URL` redirect the calls (proxies, the settings test's fake server). `MAX_CLAUDE_CALLS` caps calls per run for every provider (default 60; `--budget N` sets it for one run). `FAKE_MODEL=1` answers every prompt locally without any provider (see Scale); it is a test mode and hosted mode refuses it. Hosted mode requires the selected provider's key. Both keys are treated like auth values: scrubbed from logs, errors, summaries and exports, and removed from every child process (`claudeEnv`, `agent/frameworks/test-env.ts`). The per-call console line keeps the `[claude]` label for every provider (the UI reads it, `ui/CONTRACT.md`). The prompts were tuned against Claude; `npm run eval -- --provider openai` measures the other provider before anyone standardises on it.

`verifyProviderKey(provider, key, model?)` makes one 5-token request and returns `{ ok, provider, model, error }` with a plain sentence for 401, 402/403, 404, 429 and network failures, never the key. The UI's first-launch card uses it (section 10 of `ui/CONTRACT.md`): `GET /api/settings`, `POST /api/settings/verify`, `POST /api/settings` (verifies, then writes `LLM_PROVIDER`, `LLM_MODEL` and the key line into `.env`, mode 600, other lines kept). The POST routes are 403 whenever `HOSTED=1` or `UI_USERS` is set: a shared server never takes keys from the browser. `ENV_FILE` points the UI server at another `.env` (tests); `SKIP_CLI_DETECT=1` makes it ignore an installed `claude` CLI (tests).

## Frameworks

The output framework is an adapter in `agent/frameworks/` (`types.ts` is the interface, `playwright.ts` and `pactum.ts` the two adapters, `index.ts` picks one). The input file's optional `"framework": "playwright" | "pactum"` decides; missing means playwright. Shared and never framework-aware: importers, probe, plan, status rules, finding classification, summary, safety guard, auth handling. Per adapter: template, generator rules, static gate, runner and results parser, exporter. Every adapter returns normalized results (endpoint id, title, passed, actual status, error, requests sent); `cli.ts` only reads those.

Pactum: tests are Mocha `describe`/`it` files that import `{ ctx, expect, recordStatus }` from `tests-pactum/setup/ctx.ts` and nothing from `pactum`. `ctx.api` and `ctx.noAuthApi` return a response with `status()`, `ok()`, `headers()`, `text()` and `json()`; every request goes through one guarded `send()` that applies rule 11, counts requests and writes redacted evidence to `reports/pactum/evidence/`. `recordStatus(status)` is the Pactum equivalent of the `actual-status` annotation; a Mocha root hook writes it to `reports/pactum/status.json` and skips write endpoints in read-only mode. `expect` is a small matcher set in the setup file with the same names as Playwright's, so the per-type gate rules are shared. Runner: `mocha --config .mocharc.pactum.json` with the JSON reporter to `reports/pactum/results.json`. Export: `frameworks/<name>-pactum/` (no double suffix when the name already ends in `-pactum`). Allure: the adapter writes one Allure result file per Mocha test into `reports/pactum/allure-results/` from `results.json` and `status.json` (same epic, feature, story and severity labels as Playwright, `actual-status` as a parameter, the redacted evidence files attached), then runs the Allure CLI into `reports/allure-report/` with the same secret scan as the Playwright adapter; `allureReport` is that path, or null with `allureReason` when the report could not be built.

Both exports ship `.github/workflows/api-tests.yml` and `azure-pipelines.yml` (`agent/frameworks/shared-export.ts` `ciFiles`): Node 22, `npm ci`, the test command, the report folder uploaded as a build artifact, every auth env variable mapped from a CI secret of the same name (`AGENT_SELECT` too for a profile). The README's "Run in CI" section lists the exact secret names. The files hold names only, never a value.

## Pipeline

0. `agent/safety.ts`: classifies the base URL's host and sets the safety mode (rule 11) before any request.
1. `agent/probe.ts`: one real call per endpoint. Non-2xx is retried once, then the endpoint is marked unusable and skipped, unless sheet cases are in scope for it: then it is planned from the sheet (`plannedFromSheet`, a `WARNING probe not usable` console line and a probe warning). After the endpoint probes, `probeCases` sends one GET per sheet case with its own literal path (`pathValues`), at most `--case-probes` (default `CASE_PROBE_CAP` 20, `agent/probe-cap.ts`), never a write, never a path that needs setup, and writes `out/probes/<id>.cases.json`. `pathParams` in the endpoint config fills placeholders no setup step fills. A 429 is not retried again here (the HTTP layer already did, rule 12): the endpoint is unusable with the reason `rate limited`.
2. `agent/plan.ts`: Claude returns JSON test cases, validated with zod and against the status rules below; one retry.
3. `agent/generate.ts`: Claude writes one spec per endpoint, copying the adapter's template (`tests/template/update-booking.spec.ts` or `tests-pactum/template/update-product.spec.ts`).
4. `agent/validate.ts`: static gate (`validateWithRules` shared, framework rules from the adapter). Generated code is untrusted: only the ctx import is allowed, and `unsafeCodeReasons` rejects require, import(), eval, Function, process, globalThis, fetch, Node built-in module names and Playwright fixtures other than ctx. Prompt data from outside (endpoint config, probe, plan, ticket text) is wrapped with `untrusted()` (agent/untrusted.ts). A candidate that fails it is retried once, then dropped. Nothing unsafe is ever written to `generated/`.
5. `agent/cli.ts`: runs plans and generations `--concurrency` at a time (default 3, phase by phase), writes `out/checkpoint.json` after the probe, every plan and every spec (`agent/checkpoint.ts`), runs the adapter's runner with `--test-workers` (default 1), writes `out/summary.json` (with `testFramework` and `scope`), and the Allure report (both frameworks, built by the adapter).
6. `agent/export.ts` (Playwright) or `agent/frameworks/pactum.ts` (Pactum): writes `frameworks/<name>/` (or `<name>-pactum/`) and `out/framework.zip` (zipped in-process by `agent/zip.ts`, no `zip` program needed), then scans every file for the real auth value and fails loudly if found.

`generated/`, `out/` and `reports/` are deleted at the start of every fresh run. `--resume` and `--only-new` keep `generated/` and `out/` and delete only `reports/`.

## Scale (agent/checkpoint.ts, agent/flags.ts, agent/fake-model.ts)

A real API has hundreds of endpoints; a run must survive a budget stop or a crash without paying for finished endpoints again.

- Checkpoint: `out/checkpoint.json` holds the input hash (the whole resolved config), and per endpoint its definition hash (id, method, path, requiresAuth, body, query, headers, setup), stage (`probed`, `planned`, `generated`, `failed`), the redacted probe, the plan and the spec file name. Written atomically (temp file, rename) after the probe and after every plan and spec, so a crash never leaves a half-written file; a corrupt file is an error, never an empty checkpoint.
- `--resume`: same input file, same framework, same input hash, else it says why and starts fresh (a changed input: "use --only-new"). Every endpoint continues from its last good stage: a generated spec is kept (if the file still exists), a plan is reused, a usable probe is reused, a recorded failure is retried from the stage before it. Console lines keep their shape with a `(from checkpoint)` suffix; the run prints `resume: N of M endpoints already done (reusing P probes, Q plans, N specs)`. A budget stop prints `stopped at budget: run again with --resume to continue` and sets `summary.scope.resumable`; its status stays `stopped-budget` (or `no-tests` when it stopped before the first spec) and the exit code is 2 (tool or setup error, rule 5). Endpoints skipped because the budget was already gone are not recorded as failures, so the resume picks them up.
- `--only-new`: for a changed input, endpoints whose definition hash is unchanged are reused in full, changed or new ones are probed, planned and generated again, removed ones lose their spec; every spec in scope then runs.
- `--endpoints a,b`: probe, plan, generate and run only those (an unknown id is an error). `summary.endpoints` and `summary.scope.endpoints` list only them.
- `--budget N` (this run's `MAX_CLAUDE_CALLS`), `--concurrency N` (default 3, max 8; plans and generations in flight at once, the budget check is still atomic), `--test-workers N` (Playwright `--workers`; the tests share one live API and clean up per test, so parallel runs are safe for independent tests, but data-dependent tests may need 1; Pactum ignores it with a console note because Mocha's parallel mode would need a per-worker status file). Unknown flags are an error.
- `summary.scope`: `{ mode, endpoints, reused: { probes, plans, specs }, resumable, fakeModel, concurrency, testWorkers }` (ui/CONTRACT.md section 12); the console prints `Scope: ...` in the summary block.
- `FAKE_MODEL=1`: `agent/fake-model.ts` answers the plan and generate prompts deterministically from the endpoint config in the prompt (one case per allowed type, a spec that follows the template and the gate; `[claude] <step> <id> 0.0s fake model (call n/m)` lines). It exists so the pipeline (checkpoint, resume, budget, flags, parallel workers, both frameworks, exports, contract) is tested offline; the findings of a fake run come from how the API answers the simple requests the fake spec sends and prove nothing about the model. Hosted mode refuses it before any request. `FAKE_MODEL_DELAY_MS` and `FAKE_MODEL_STATS_FILE` serve the concurrency test.
- The UI selects every imported endpoint (the 12 endpoint cap is gone) and warns above 50 with the estimated calls; `--resume` is not in the UI yet (terminal only).

## Redaction (agent/redact.ts)

Client request and response data is redacted before it reaches Claude or the disk. The real bodies live only in memory for the test run's own assertions.

- Built-in rules, always on: email addresses, phone numbers (with a `+` prefix or separators; a bare run of digits is an id and stays), card numbers (13 to 19 digits that pass the Luhn check, so order numbers and epoch timestamps stay; a run of one repeated digit is not a card), IBANs, JWTs, `Bearer`/`Basic` values and prefixed API keys (`sk-...`, `ghp_...`), IPv4 and IPv6 addresses, any string in a field named like a credential (token, secret, key, password, authorization, session, cookie, ...), and the value of any header named like one. Keys, status codes, booleans, nulls, timestamps and array lengths are never changed. UUIDs (8-4-4-4-12 hex, the all-zeros nil UUID included) are ids and are never redacted as a card, phone or IP: they are set aside after the token rules (Bearer, key prefixes, JWT) and put back, so a fixed test value reaches the plan and the tests as written; a credential-named field or header is still hidden whatever it holds (`npm run test:redact`).
- Per input file, optional: `"redaction": { "fields": ["customer.name", "address.*", "items.*.note"], "mode": "strict" }`. `fields` are dot paths (`*` matches one segment, array indexes included) whose values become `<redacted>` wherever they appear in a body. `strict` replaces every string in a response body with `<string:len>` and every number with `<number>` and keeps only the shape, for a client who allows the shape but not the data.
- Response values become tags (`<email>`, `<card>`, `<token>`, `<ip>`). Request sample bodies (from the input file; the generated tests copy them) get valid stand-ins instead (`redacted@example.com`, `+10000000000`, `4111111111111111`), so a test still sends a body the API accepts. Both are idempotent.
- Where it runs: `agent/probe.ts` redacts every probe result before it is written to `out/probes/` or returned (so the plan and generate prompts only ever see redacted probes); `plan.ts` and `generate.ts` show the endpoint config through `promptEndpoint`; `agent/claude.ts` runs the built-in rules once more over every prompt right before it leaves the process (importer text, error messages); `formatExchange` (Playwright attachments) and `writeEvidence` (Pactum evidence files) redact what they write. Counts go to `summary.redaction` and the console (`redaction: standard, N value(s) replaced` after the probe lines; `Redaction: ...` in the summary block). `agent/redact.ts` has no imports and is copied into both exports as `src/redact.ts`.
- Known false positives, accepted: a dotted version such as `1.2.3.4` reads as an IP; a Luhn-valid 13 to 19 digit id reads as a card.

## Test data cleanup

`createResource` (both frameworks) records every resource it makes `{ endpointId, id, params, source: "setup" }`. The HTTP layer also records what test code creates directly: a 2xx response to a POST sent through `ctx.api` or `ctx.as(role)` whose path matches a POST endpoint that has a paired DELETE endpoint is recorded with `source: "test"` (the id comes from the paired setup step's `idField` when one names that endpoint, else the top-level `id`, `_id` or `uuid`, or the same under `data`; a response without one is not recorded). The probe's own POST request is recorded the same way. `noAuthApi` requests and non-2xx responses are never recorded. At the end of each Playwright test (the ctx fixture, after `use`) and each Mocha test (the root `afterEach` hook), and after the probe, `cleanupResources` deletes them newest first (a review before its product) through the same guarded clients, so read-only mode and the production guard apply. The DELETE endpoint is the setup step's explicit `cleanup: { endpointId }` when given, else the DELETE whose path is the create endpoint's path plus one placeholder (`POST /products` pairs with `DELETE /products/{id}`; placeholder names may differ). A 2xx or a 404 counts as deleted; anything else is a failure with its reason. Totals go to `summary.cleanup` (`created = deleted + failed + skippedNoDeleteEndpoint`, `createdByTests` says how many of `created` were direct POSTs, `failures[]`) and the console (`cleanup: created N (M by test code), deleted N, failed N, no delete endpoint N`, the bracket only when M > 0); a failed cleanup never fails the run and is never hidden. `FAIL_DELETE_IDS=5,6` on the local API (test hook, not a planted bug) makes DELETE answer 500 for those ids, for `npm run test:cleanup`. `RATE_LIMIT_FIRST=N` (test hook) makes the first N `GET /products` answer 429 with `Retry-After: 1`, for `npm run test:http`.

## Rules that must never be broken

1. Never edit files in `generated/` by hand. Fix the instructions in `plan.ts` or `generate.ts` instead.
2. Never change an expected status to make a test pass. A failing test may be a real API bug.
3. Status rules: happy and schema expect the exact 2xx from the probe, unless a sheet case names its own code: then the sheet decides (`sheetStatusDecision` in `agent/plan.ts`), the probe only shows the response shape, and a different probe status becomes a `probeNote` (a probe warning, never a dropped case). invalid-input expects any 4xx; auth expects 401 or 403; authz (another role tries the request) expects 403 or 404. A test never expects a 5xx, except a sheet case documented by the team (a `Documented 5xx` column or the tag `@documented-5xx`): it expects exactly the sheet's code, is marked `accepted5xx` in the plan (only the agent sets it from the sheet, never the model), the gate allows only that code (`ValidateOptions.accepted5xx`), and a pass shows as `accepted 5xx`. A known issue's 5xx is never accepted.
4. Finding classification: "suspected API finding" only when the actual status is 500 or higher, or an auth, authz or invalid-input test got a 2xx. Everything else is "needs review". No `actual-status` annotation means never an API finding. A known issue (sheet Known issue column with a Jira key) that fails as expected is not a finding; one whose test passes is an "unexpected pass" finding, always "needs review".
5. A failure must never look like a pass: no empty catches, no default plans, zero specs means "NO TESTS GENERATED". Skipped, blocked, manual and known-issue tests are never counted as passed and are always listed with a reason code (`agent/test-data.ts` REASON_CODES) in the console, `summary.skippedTests` / `summary.knownIssues`, traceability and the UI. Exit codes (`agent/exit-codes.ts`): 0 clean, 1 findings (`--fail-on finding`, the default; `--fail-on skipped` also fails on any skipped, blocked or manual test; `--fail-on none` reports them and exits 0), 2 tool or setup error (refused, no-tests, stopped-budget, an endpoint not tested, failed export, crash). `out/summary.json` is written before the framework export and keeps `exitCode`, `failOn` and `frameworkError`.
6. Auth values (header, query and cookie values, login credentials, issued tokens) come only from `.env` or the UI (env `CUSTOM_API_AUTH`, one run only). They must never appear in input files, summaries, reports, attachments, logs, the Claude prompts or the exported framework. The Claude CLI child process gets no env variable with AUTH in its name. Imported configs must never contain auth values (header values, cookies, tokens): importers drop them, keep only the credential's name and place (`auth.header` / `auth.param` / `auth.name` and `auth.valueEnv`), and warn naming what they dropped. See Auth below for how values are scrubbed.
7. `tests/fixtures/ctx.ts` (Playwright) and `tests-pactum/setup/ctx.ts` (Pactum) are the only test-side files that read `process.env` or the input file, and they read only the variables the auth section names (`pickAuthEnv`). They parse `.env` into a private object (never `dotenv/config`), so the model provider keys never reach the test process (`npm run test:security`). Tests use `ctx.api`, `ctx.noAuthApi`, `ctx.as(role)`, `ctx.createResource(endpointId)`, `ctx.setup()`. Pactum tests never import `pactum`, so the guard in `send()` covers every request.
8. The UI reads agent output exactly as described in `ui/CONTRACT.md` (console phase headers, per-endpoint OK/FAILED lines, `out/summary.json` shape, the report and evidence files). Any change to agent output must keep that contract, and any change to `ui/` must keep reading the agent through it: the UI validates inputs with the agent's own schema (`agent/config.ts` via tsx) and never changes the agent for its own needs. `ui/index.html` stays one self-contained file: no build step, no framework, no external fonts or scripts.
9. The exported framework must stay standalone: no imports from `agent/` or outside its own folder.
10. Never commit `node_modules/`, `out/`, `reports/`, `generated/`, `test-results/`, `frameworks/*` (except `frameworks/.gitkeep`), `.env` or `.DS_Store`. `.gitignore` covers them. Run `git status` before every commit and confirm none of them are listed.
11. Production safety guard (`agent/safety.ts`). A login request (auth type `login`) is not a data write: it is sent in read-only mode too, through the same guarded path (counted, recorded with credentials and token redacted); in refused mode nothing is sent, the login included. The host is local (localhost, `.local`, host.docker.internal, and the addresses of this machine or a private network: 127/8, 0/8, 10/8, 100.64/10, 169.254/16, 172.16/12, 192.168/16, ::, ::1, fc00::/7, fe80::/10 and IPv4-mapped forms of those), non-production (a whole part, split on "." and "-", is dev, test, qa, staging, stage, sandbox, uat or preprod) or production (everything else). Local and non-production: mode "full". Production without `allowProduction`: "refused", no request is sent, status "refused", exit 2. Production with `allowProduction`: "read-only", only GET, HEAD and OPTIONS endpoints without setup run, the rest are "skipped: read-only mode" and never counted as passed. With `allowWrites` as well: "full" plus the WARNING line. The guard lives in the shared HTTP layer (`agent/http.ts` `createClients`), so it covers probe, `createResource`, the ctx fixture and the exported framework; never bypass it with a client made elsewhere. Nothing may make a production host count as local or non-production. `ui/host-class.mjs` must keep the same rules (checked by `npm run test:safety`). The CLI also resolves the host name once (`agent/resolve-host.ts`); the result can only make the guard stricter: a name that resolves to a local or private address keeps its class by name, prints `safety note: ...`, and is refused in hosted mode. An absolute OAuth2 `tokenUrl` on another host is classified the same way: a production token host is refused unless the input allows production.
12. 429 handling lives in the shared HTTP layer (`agent/http.ts` `guarded`, `tests-pactum/setup/ctx.ts` `send`, so the probe, both ctx files and both exports behave the same). A 429 is sent again after `Retry-After` (seconds or an HTTP date, capped at 60 s) or 1 s, 2 s, 4 s, at most 3 retries; every retry counts as a request sent; after the last retry the 429 is the actual status (a test fails, never passes). A write that answered 429 was not processed, so it is safe to send again; a write that answered anything else is never retried. The probe marks an endpoint still 429 unusable with the reason `rate limited`.

## Auth (`agent/auth.ts`)

One module with no imports, copied into both exports as `src/auth.ts`, so the agent, both ctx files and both exported frameworks apply auth the same way. The input's `auth` section has a `type`; without one it is the original `{ header, valueEnv }` form.

| Type | Shape | What is sent |
|---|---|---|
| `header` (default) | `{ "header": "Authorization", "valueEnv": "API_AUTH_VALUE" }` | the header with the whole value from env (prefix included, for example `Bearer x`) |
| `query` | `{ "type": "query", "param": "api_key", "valueEnv": "API_KEY" }` | `?api_key=<value>` on every request |
| `cookie` | `{ "type": "cookie", "name": "session", "valueEnv": "SESSION_COOKIE" }` | `Cookie: session=<value>` |
| `login` | `{ "type": "login", "request": { "method": "POST", "path": "/auth/login", "body": { "remember": true }, "headers": {} }, "credentialsEnv": { "username": "ADMIN_USER", "password": "ADMIN_PASSWORD" }, "tokenPath": "data.token", "apply": { "type": "header", "header": "Authorization", "prefix": "Bearer " }, "refresh": { "statuses": [401], "once": true } }` | the login request once per client (credentials from env merged into the body), the token read at `tokenPath` (a dot path) and applied as a header, cookie (`apply.type: "cookie", name`) or query parameter (`apply.type: "query", param`); on a `refresh.statuses` response the login is repeated and the request sent once more |
| `oauth2_client` | `{ "type": "oauth2_client", "tokenUrl": "/oauth/token", "clientIdEnv": "SHOP_CLIENT_ID", "clientSecretEnv": "SHOP_CLIENT_SECRET", "scope": "read write", "audience": "...", "clientAuth": "body", "tokenPath": "access_token", "apply": { "type": "header", "header": "Authorization", "prefix": "Bearer " }, "refresh": { "statuses": [401], "once": true } }` (everything after `clientSecretEnv` optional, the values shown are the defaults) | a form-encoded `grant_type=client_credentials` POST to `tokenUrl` (a path on the API host, or an absolute URL whose host the guard classifies, rule 11) with `client_id` and `client_secret` in the form (`clientAuth: "body"`) or as HTTP Basic (`"basic"`), plus `scope` and `audience` when given; the access token at `tokenPath` is cached and applied like a login token, refreshed once on a `refresh.statuses` response. Roles: `"roles": { "viewer": { "clientIdEnv": "...", "clientSecretEnv": "..." } }` |

- Roles: `"roles": { "viewer": { "valueEnv": "VIEWER_KEY" } }` for header, query and cookie; `"roles": { "viewer": { "credentialsEnv": { "username": "VIEWER_USER", "password": "VIEWER_PASSWORD" } } }` for login (same fields as the main `credentialsEnv`). The main section is the role `default`; `default` cannot be a role name. Tests call `ctx.as('viewer')` (an `APIRequestContext` in Playwright, a `Client` in Pactum); the probe and `createResource` use the default role.
- `[authz]`: allowed only for endpoints with `requiresAuth` when the input has at least one extra role. The plan expects `"403|404"`; the gate requires `ctx.as('<role>')` and `expect([403, 404]).toContain(status)` and rejects `ctx.api`, `ctx.noAuthApi` or a 2xx expectation; a 2xx actual status is a suspected API finding (rule 4). Eval bugs can be `detectableBy: "authz"`.
- Secrets: `secretValues` (header, query and cookie values, and login fields whose name looks secret: password, pass, pwd, secret, token, key, ...) plus every issued token are scrubbed from evidence, error text, summaries and exports. A plain username such as `admin` is not scrubbed from every text (it would also hit role names); the login request evidence redacts every credential field instead, and the login response evidence redacts the token at `tokenPath`. Sensitive header names (the auth header, Authorization, Cookie) and the auth query parameter are shown as `<redacted>`.
- Login failures (non-2xx, no JSON, nothing at `tokenPath`, a missing env variable) throw with the reason and role before any test request; nothing falls back to an empty value.
- Playwright creates one set of clients per test, so the login runs once per test (tests stay independent); Pactum's setup file logs in once per Mocha process. The exported frameworks behave the same.
- Importers map OpenAPI `securitySchemes` and Postman auth blocks: apiKey in header, query or cookie to the matching type; http bearer to a header with a warning about the `Bearer ` prefix; oauth2 with a `clientCredentials` flow (Swagger 2.0: `flow: application`) to `oauth2_client` with the flow's `tokenUrl` and `CUSTOM_API_CLIENT_ID` / `CUSTOM_API_CLIENT_SECRET` as the env names (a warning says so); other oauth2 flows and openIdConnect to a header with a warning to configure the login or oauth2_client type by hand. Values are never imported.
- Secrets for `oauth2_client`: the client secret, the Basic value and every access token are scrubbed from every text; the client id is redacted in the token request evidence only (like a username).
- Not covered yet in the UI's Build tab: `oauth2_client` (use a saved input; the UI validates every type and roles with the agent's schema). Values other than the one-run header, query or cookie value come from `.env`, and the page lists the variable names it will read.
- `input/local-shop-login.json` is the proof input: `POST /auth/login` on the local shop API with users `admin` (writes) and `viewer` (reads only), planted bug `viewer-can-delete`. The demo credentials are in `.env.example` (`LOCAL_API_ADMIN_USER`, `LOCAL_API_ADMIN_PASSWORD`, `LOCAL_API_VIEWER_USER`, `LOCAL_API_VIEWER_PASSWORD`).
- `input/local-shop-oauth.json` is the OAuth2 proof input: `POST /oauth/token` on the local shop API (client `shop-client`, secret from `LOCAL_API_CLIENT_SECRET`, demo value in `.env.example`; the issued token acts as admin). Wrong client: 401 `invalid_client`; wrong grant: 400 `unsupported_grant_type`.

## Hosted mode (`HOSTED=1`)

For the UI running on a shared server (the SprintSynergy VPS, `docs/HOSTING.md`). Every rule below can only make the agent stricter; without `HOSTED` and without `UI_USERS` nothing changes for the local demo.

| Variable | Meaning |
|---|---|
| `HOSTED=1` | hosted mode on, for the UI server and the agent it spawns (the agent reads it too: `agent/safety.ts` `isHosted()`) |
| `HOST` | bind address; anything but `127.0.0.1` or `localhost` needs `HOSTED=1`, otherwise the server exits 1. Behind Nginx keep the default |
| `UI_PORT` | UI port (default 3000) |
| `UI_USERS` | `name:bcryptHash,name2:bcryptHash` from `npm run ui:hash -- <password>`. Sets login on, hosted or not. Required with `HOSTED=1` |
| `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` | the selected provider's key is required with `HOSTED=1`: the shared server never uses a personal Claude login |
| `HOSTED_RUNS_PER_HOUR` | runs per login per hour (default 5); over it `POST /api/run` is 429 |
| `HOSTED_QUEUE` | runs waiting behind the one in progress (default 5); over it 429 |
| `HOSTED_RUN_TTL_HOURS` | run folders older than this are deleted hourly (default 24) |

Rules in hosted mode (`agent/safety.ts`, mirrored in `ui/host-class.mjs` `safetyMode`, tested by `npm run test:safety`):
- a local or private host (rule 11's "local" class) is refused with `REFUSED: <host> is a local or private address; the hosted agent only tests public non-production hosts.` It would be the server's own network
- a production host never gets full mode: `allowWrites` is ignored, `allowProduction` gives read-only as before
- non-production hosts run in full mode as before
- `HOSTED=1` in the environment applies everywhere (probe, ctx fixture, export, UI); `hosted: false` as an option cannot switch it off

Login and isolation (`ui/server.mjs`), on whenever `UI_USERS` is set:
- `POST /api/login` sets an HttpOnly, SameSite=Strict session cookie (Secure when Nginx sends `X-Forwarded-Proto: https`); sessions live in memory for 12 hours. Every `/api/*` route except session, login and logout, plus `/report` and `/allure`, is 401 without it. Static files stay public
- each run gets `runs/<runId>/` (gitignored): its `input.json`, then a snapshot of `summary.json`, `framework.zip`, `html/`, `allure-report/`, `generated/`, `results.json` and `pactum/` when it ends. `/api/summary`, `/api/spec`, `/api/framework/download`, `/api/evidence`, `/report` and `/allure` serve the caller's latest run (or `?run=<id>` when it is theirs); `/api/runs` lists only the caller's runs. The live stream and stop only reach the run's owner. Local mode (no login) writes the same snapshots for the run history and keeps the newest 20
- runs still execute one at a time (the agent writes fixed paths); a second login's run is queued and starts automatically. One run in progress or queued per login
- `POST /api/inputs/save` is 403 in hosted mode: saved APIs are shared by every login

## Static gate (agent/validate.ts) rejects a spec when

Shared rules (both frameworks) plus the framework rules in each adapter. Pactum adds: must import `ctx`, `expect` and `recordStatus` from the setup file; no `pactum`, `node:assert` or `chai` import; no `.only`, `.skip`, `xit`, `xdescribe` or `this.skip()`.

- it does not import `test` and `expect` from the ctx fixture, or imports from `@playwright/test` directly
- it contains `process.env`, `http://` or `https://`
- it contains `test.only`, `test.skip`, an empty catch, a catch that does not rethrow, or `.catch(`
- a title does not start with `[happy]`, `[schema]`, `[invalid-input]`, `[auth]` or `[authz]`
- a test lacks the `actual-status` annotation before its first assertion
- any assertion expects a status of 500 or higher
- it has fewer tests than plan cases, fewer tests of a type than the plan has cases of that type, or fails typecheck
- a status assertion does not match the test's type, or a required one is missing. The only allowed forms, per type: `[happy]` and `[schema]` exactly `expect(<status>).toBe(<probe status>)`; `[invalid-input]` `toBeGreaterThanOrEqual(400)` and `toBeLessThanOrEqual(499)`, both required; `[auth]` `expect([401, 403]).toContain(<status>)` (or `toBe(401)` / `toBe(403)`). `<status>` is `response.status()` or a variable assigned from it. `.not` on a status is never allowed
- a `[happy]` or `[schema]` test asserts only the status: it needs at least one assertion on the response body (a field value or type from `response.json()` / `.text()`, not just `toBeDefined()` or `toBeTruthy()`). Lifted when the probe got no body or a 204, 205 or 304
- a `[schema]` test does not assert every required field of the endpoint's documented `responseSchema` (when the probe status is the documented one)
- an `[auth]` test mentions `ctx.api` (or destructures `api` from ctx), or does not use `ctx.noAuthApi`
- an `[authz]` test does not use `ctx.as('<role>')`, mentions `ctx.api` or `ctx.noAuthApi`, or asserts anything but `expect([403, 404]).toContain(<status>)` (or `toBe(403)` / `toBe(404)`)

- (Playwright) it contains `test.fixme`, `test.fail`, `test.slow`, `test.info().skip|fail|fixme|slow`, `testInfo.skip|fail|fixme|slow` or `ctx.requireData(`; (Pactum) `knownIssue(` or `requireDataFor(`. Those markers are added only by the agent after the gate (`addCaseMarkers`, `skippedBlock` in `agent/generate.ts`) from the sheet's Known issue / Required data / Automation columns and the test data file, never by the model

Additions (agent/validate.ts, agent/generate.ts):
- `[invalid-input]` may also assert a list of 4xx codes, `expect([400, 404]).toContain(<status>)` (the sheet's own codes, plan `statusCodes`), on top of the two required range checks; a 5xx in the list is still rejected
- non-JSON probe (`probeContentType`, an image or file): a header (`response.headers()[...]`), `response.body()` size or file signature assertion counts as the body check; `response.json()` must not be used on it
- reasons are per test (`byTest`) or for the file (`fileReasons`: imports, framework rules, code outside the tests). After the retry, `pruneFailingTests` removes only the rejected tests and re-validates the rest; each dropped case goes to `plan.notAutomated` with its own reason. Any file reason still rejects the whole spec, and `byTitle` keeps each case's reasons for traceability
- coverage: a sheet case's clauses (`plan.ts` `clausesFor`, from the model's `coverage`) count as asserted only when the test has `// covers clause N` followed by an `expect`; otherwise `not-asserted`. A passed test with a not-asserted clause is `partially covered`, with a `probe-disagrees` clause `needs review` (agent/traceability.ts). Never report such a case as passed
- cross-call tests (plan `crossCall`) only when `dataStability` says stable (read-only GET with no writer of the same resource in the run, or `stableData`); each such case is one test that sends every call it compares. No serial mode: the gate rejects `test.describe.configure({ mode: 'serial' })` and `test.describe.serial` (one failure there skips every later test in the file), so tests never depend on each other or on order
- URLs: every request path is joined to the base URL with `joinUrl` (agent/model.ts), never `new URL(path, base)`, so a base URL path is kept

## Eval harness

`local-api/bugs.json` is the catalog of planted bugs in the local shop API (id, description, endpointId, detectableBy). `local-api/server.mjs` reads its ids: `BUGS` unset turns on the catalog's `default` set (the two original demo bugs, so every existing verification step is unchanged), `FIXED=1` turns every bug off, `BUGS=id,id` turns on exactly those. Startup prints `bugs ON: <ids>` or `bugs OFF`. An unknown id exits 1.

The local API also has `POST /auth/login` (users admin and viewer, see Auth) and the planted bug `viewer-can-delete` (`detectableBy: "authz"`).

`npm run eval` (`agent/eval/run.ts`) starts the local API itself on a free port for each bug set (default matrix: all bugs, no bugs, each detectable bug alone), runs the agent N times (default 3) on a copy of `input/local-shop-login.json` pointed at that port, and scores every valid run with `agent/eval/score.ts`. The login input is used because it has a second role (viewer): without one no `[authz]` test is written and `viewer-can-delete` could never be detected. `.env` needs the four `LOCAL_API_*_USER` / `_PASSWORD` values from `.env.example`.

- detected: a "suspected API finding" exists for the bug's endpoint with the bug's type (invalid-input bugs need an invalid-input finding, auth bugs an auth finding, authz bugs an authz finding)
- false alarm: a suspected finding no active bug explains
- flaky: runs in the same bug set whose suspected finding sets differ
- not-yet: bugs with `detectableBy: "none-yet"` (needs a test type the agent does not have); reported, never counted against detection
- preflight (`agent/eval/preflight.ts`), once per bug set and without the model: every endpoint must probe usable and every extra role must be able to log in. When it fails no agent run starts for that set (no model call is paid for), every run of the set is recorded as invalid with the reason, and the console prints which `.env` variables the eval reads
- a run is scored only when it is valid (`runValidity` in `agent/eval/score.ts`): the agent wrote a summary, its status is `completed`, and every endpoint of the input was tested (no `failureReason`, no `skippedReason`, a spec written). An endpoint that was not probed, or whose spec the gate dropped, makes the whole run invalid. An invalid run gets no score at all (`score: null` and an `error` in `score.json`), is printed as `INVALID <reason>`, is left out of every rate, and fails the eval (exit 1). The table's `valid runs` column and the `runs scored N/M` line show how many runs the rates rest on; with no valid run the eval prints `no valid run, so there is no score`. Never quote a rate from an eval that exited 1 without reading which runs were invalid. `flaky` is judged on valid runs and is `n/a` with fewer than two

Output goes to `eval-results/<timestamp>/` (gitignored; not under `out/`, which the agent deletes every run): per set `input.json`, `run-N.log`, `run-N.summary.json`, plus `score.json` (with `input`, the template the runs used). `EVAL_RESULTS_DIR` moves the folder (the tests use it). Adding a planted bug: add it to `bugs.json`, implement it in `server.mjs` behind `bug("<id>")`, add its probe to `agent/eval/eval.test.ts` (the test fails until every catalog bug has one).

## Input files

`input/endpoints.json` and `input/demo-small.json` (Restful Booker), `input/local-shop.json` (local demo API), `input/local-shop-pactum.json` (the same with `"framework": "pactum"`), `input/local-shop-nested.json` (local demo API with the nested reviews resource, query and headers), `input/local-shop-login.json` (local demo API with the login auth type and a viewer role), `input/local-shop-oauth.json` (the same API with the oauth2_client type), `input/example-profile.json` (a profile with placeholder hosts), `input/local-shop-sheet.json` (local demo API with the sample test case sheet `input/local-shop-test-cases.csv`; `input/test-cases-template.csv` is the template the UI serves). Shape: optional `name`, optional `framework` ("playwright" or "pactum", default playwright), `baseUrl` or `profile` (below), `defaultHeaders`, optional `auth` (`{ header, valueEnv }` or one of the types in Auth above, with optional `roles`), optional `allowProduction` and `allowWrites` (booleans, false when missing, rule 11), optional `redaction { fields?, mode? }` (see Redaction), optional `testCases { file | link, mode? }` (see Test case sheets and Test cases from links), `endpoints[] { id, method, path, requiresAuth, body?, query?, headers?, setup? }`. A setup step may carry `cleanup: { endpointId }` naming the DELETE endpoint for what it creates (see Test data cleanup). Do not overwrite the kit files.

- `path` holds `{placeholders}` only, never a query string. `query` is an object of string, number or boolean values (arrays and objects are refused); `headers` are extra headers for this endpoint. The probe, `createResource` and the generated tests send both (`params` and `headers` request options on `ctx.api` in both frameworks). The auth header is added last and never comes from these fields (rule 6).
- `setup` is one `{ endpointId, idField }` (fills the first placeholder, the original shape) or an array of `{ endpointId, idField, param }`, one step per placeholder in order. Steps run in order and each step sees the ids collected so far, so `POST /products/{id}/reviews` creates its review under the product made one step earlier. Tests for a path with more than one placeholder call `ctx.setup()` and get `{ id, reviewId }`; single-placeholder tests keep `ctx.createResource(endpointId)`.
- `profile` describes one API across environments, brands and regions: `{ dimensions: { env: [...], brand: [...], region: [...] }, baseUrl: "https://{brand}-{region}.{env}.example.com", headers: { "X-Brand": "{brand}" }, overrides: [{ when: { region: "eu" }, headers: {...}, baseUrl?: "..." }] }`. `--select env=staging,brand=alpha,region=eu` (or `AGENT_SELECT`) picks exactly one value per dimension; a dimension with a single value is picked on its own; anything else stops with an error listing the dimensions and values (`npm run agent` exits 2, rule 5; `npm run probe` exits 1). `agent/model.ts` resolves it once in `loadConfig`, so everything downstream (the safety guard included) sees a plain `baseUrl` and `defaultHeaders` (order, later wins: defaultHeaders, profile headers, matching overrides in order). The summary gets `selection` (`ui/CONTRACT.md`), the console prints `selection: env=staging, ... -> https://...`. Exported frameworks keep the profile block in `config/api.json` and read `AGENT_SELECT` at run time, so one export serves every brand and region.
- Real client profiles live only in `profiles/local/` (gitignored, see `profiles/README.md`); `input/example-profile.json` uses placeholder hosts only. Never commit a client host or header value.
- `agent/model.ts` holds the pure helpers (`resolvePath`, `setupSteps`, `queryString`, `resolveProfile`) and has no imports: both exporters copy it as `src/model.ts`. The two Restful Booker files set `allowProduction` and `allowWrites` true: Restful Booker is a public sandbox meant for writes, but its host counts as production. `input/import-openapi-local-shop.json` and `input/import-postman-local-shop.json` are imported from the local shop fixtures (`auth.valueEnv` set to `LOCAL_API_AUTH_VALUE` so they run with `.env`) and must give the same results as `input/local-shop.json`.

## Importers

`agent/import.ts` plus `agent/importers/` (`core.ts` shared, one file per format) turn an existing API description into the input file shape, validated with the same zod schema.

| Type | Source |
|---|---|
| `openapi` | OpenAPI 3.x or Swagger 2.0, JSON or YAML |
| `postman` | Postman collection v2.0 / v2.1 |
| `curl` | one or more curl commands |
| `har` | browser network capture (static assets, analytics and other origins filtered out) |
| `text` | Jira / Confluence text; Claude extracts it, at most 2 calls, outside the run budget |

- Command: `npm run -s import <type> < file`. It reads stdin and prints one JSON object `{ input, skipped, warnings }` on stdout. It writes no file; to make an input file: `npm run -s import openapi < spec.yaml | jq '.input' > input/<name>.json` (keep `-s`: without it npm's banner breaks the JSON). Nothing importable: exit 1, reason on stderr.
- The UI uses the same CLI through `POST /api/import` (Import tab, Source). See `ui/CONTRACT.md` section 6. The page's other routes for inputs, run history and evidence are section 11.
- Base URL: the most common origin; requests to other origins are skipped. Empty when the source has none, with a warning.
- Path parameters: `{id}`, `:id` and `{{id}}` become `{id}`; in HAR, numeric and UUID segments become `{id}`.
- Query parameters become the endpoint's `query` object (OpenAPI: required ones always, optional ones only with an example or default; Postman, cURL and HAR: the URL's query, HAR keeps the query of one request per grouped endpoint). Non-credential, non-transport headers become the endpoint's `headers`, with a warning to check the values.
- Bodies: JSON objects only. Form, XML and other bodies are skipped with the reason. OpenAPI uses the example, else builds one from the schema's required fields.
- Setup: each placeholder gets a step from the POST on its parent path (`POST /products` for `{id}`, `POST /products/{id}/reviews` for `{reviewId}`); one placeholder keeps the single-object shape, more give an array with `param`. A warning asks to check `idField`.
- Auth: credentials are dropped (Authorization, Cookie, any header with auth/token/key/secret/session in its name, Postman auth blocks, curl `-u`/`-b`, credential query params, URL userinfo). Those endpoints get `requiresAuth: true` and the input gets an auth section with `valueEnv: "CUSTOM_API_AUTH"`: `{ header, valueEnv }` for a header credential (the most common one wins), `{ type: "query", param, valueEnv }` for a query credential, `{ type: "cookie", name, valueEnv }` for an OpenAPI apiKey cookie. Nothing is dropped silently: every skipped item has a reason.
- Body fields named like credentials (password, pass, pwd, secret, token, ...) are replaced with `<removed>`. The text importer makes at most 2 Claude calls, and never more than `MAX_CLAUDE_CALLS`.
- Tests: `npm run test:importers` (`agent/importers/importers.test.ts`, plain `node:assert` via tsx, no Playwright). Runs offline; the two tests that make live Claude calls run only with `RUN_LIVE_CLAUDE_TESTS=1` (`claude` must be logged in). Fixtures are in `test-fixtures/importers/` and use only the fake credential `importer-secret-test-value`.

## Test case sheets (agent/test-cases.ts, agent/match-cases.ts, agent/traceability.ts)

- `--test-cases <file>` (or `testCases: { file, mode }` in the input, file relative to the input) loads the team's sheet: `.csv`, `.tsv`, `.txt` or `.xlsx` only (never any other file). Columns map by alias (`mapColumns`); a row never disappears: no ID gets `ROW-<n>`, an unmatched case is `not automated` with the reason. XLSX is read with `read-excel-file` (stored values only, formulas never run) after `checkXlsxContainer` checks the zip directory (60 MB uncompressed, 2000 parts); 5 MB, 1000 cases, 100 columns, 4000 characters per cell.
- Matching: Endpoint column, then a `METHOD /path` in the steps (`matchExplicit`), then one model call per 25 cases (`matchCases`, step `match`, counted in the budget). The sheet text is untrusted in every prompt.
- Titles: `[<ID>] [<type>] <Title>` for sheet cases, `[agent] [<type>] ...` for suggestions (`sheetTitle`, `agentTitle`); `parseTestTitle`/`testTypeOf` in `agent/model.ts` read both, and every type rule of the gate still applies. Rules 2 and 3 win over the sheet: a case that expects a 5xx, contradicts the probe status or needs a type the endpoint cannot have is marked needs review by `finalizeSheetPlan`, never forced. Needs-review placeholders (`test.fixme` / pending `it`) are appended by the agent after the gate (`needsReviewBlock`), never written by the model; they do not change the exit code.
- Modes: `sheet-plus-agent` (default; agent cases only for what the sheet misses, repeats dropped by `duplicatesSheetCase`) and `sheet-only` (no agent cases; only endpoints with cases are probed). The checkpoint key includes the sheet hash and mode.
- Output: `out/traceability.csv` and `.xlsx`, `summary.testCases` (ui/CONTRACT.md section 15), Allure `caseId` labels, `traceability.csv` in the export.
- Statuses and reason codes (agent/test-data.ts, agent/test-cases.ts `prepareSheetCases`, agent/frameworks/types.ts `outcomeKind`): the test data file (`--test-data`, input `testData`; `{ environment?, values, lookup?: { endpointId, query? } }`, lookup must be a GET endpoint) fills `[PLACEHOLDER]` names; a missing value is skipped `MISSING_TEST_DATA`; an Automation cell saying manual is `MANUAL` / `MANUAL_VISUAL`. Those declared skips never reach the model (`planWithSheet` adds them back as `skipped` placeholders). Required data is checked at run time by `ctx.requireData` (Playwright, `testInfo.skip`) or the `requireDataFor` registry (Pactum, root `beforeEach`): `DATA_NOT_ON_ENV` or `ENV_UNAVAILABLE` means **blocked**. A Known issue cell needs a Jira key (else a warning, ignored); the case keeps the correct non-5xx status from the sheet (the probe conflict check is bypassed for it) and is wrapped in `test.fail(true, "KNOWN_ISSUE ...")` / `knownIssue("KNOWN_ISSUE ...", ...)`. Outcome kinds: passed, failed, blocked, known-issue, unexpected-pass. Only failed and unexpected-pass make findings. `summary.totals.passed + failed + blocked (run) + knownIssues === testsGenerated`. A model-supplied `MANUAL` code is dropped (only the sheet declares manual).
- Traceability columns: ID, Title, Endpoint, Test file, Status, Reason code, Coverage, Reason, Jira, Confluence. Test file is blank unless a runnable test automates the case (never the file of a needs-review placeholder or a gate-dropped case). Reasons are never shortened in the files or the summary (the console may wrap them). Coverage is `asserted/clauses (percent%)` for cases with a test; `summary.testCases.assertionCoverage` = `{ asserted, clauses, percent }` over every sheet clause (cases without a test count as not asserted). Jira / Confluence come from sheet columns (`jira`, `confluence` fields in `test-cases.ts`, set only when not empty so older sheet hashes stay) or the Atlassian import (Jira browse link, Confluence page link, Zephyr key).
- Response format: `expectedContentType()` (`agent/expected.ts`) reads a media type, "JSON" or "plain text" from a sheet case's expected result (ruled-out or request formats ignored) into plan case `contentType`. The gate (`checkContentType` in `validate.ts`, shared by both adapters) then requires an `expect` on the Content-Type header containing `json` (any JSON type) or the media type, and rejects `.json()` in a test for a format that is not JSON.
- Report font: the UI and the HTML reports the agent builds (Playwright HTML report, Allure report; `agent/report-font.ts` adds one `<style>` before `</head>`) use `Calibri, Carlito, 'Segoe UI', Arial, sans-serif`. ## Test cases from links (agent/atlassian.ts)

- `--test-cases <link | jql: ... | JQL | zephyr: ...>` or `testCases: { link }` (`isLinkSource` decides). `loadLinkCases` turns Jira issues, Confluence tables and Zephyr Scale cases into canonical rows and calls `casesFromRows`, so everything after loading is the sheet path; `ParsedSheet.format` is `jira`, `confluence` or `zephyr` and `source` says what was read.

## Known environment notes

- macOS, Windows and Linux are all supported, and CI runs every offline suite plus `npm run test:e2e` on all three (Node 22 and 24). Rules that keep it so: start dev tools through `agent/node-bin.ts` (`process.execPath` plus the package's JS entry, never `node_modules/.bin`), start the Claude CLI through `agent/claude-bin.ts`, stop child processes with a tree kill on Windows (`killTree` in `ui/server.mjs`), build paths with `path.join`, and keep LF line endings (`.gitattributes`). If Allure cannot generate a report on a machine, the run continues with `allureReport: null`.
- If port 3000 or 4000 is busy: `lsof -ti tcp:3000 -sTCP:LISTEN | xargs kill` (or `tcp:4000`). Without `-sTCP:LISTEN`, lsof also lists clients connected to the port, such as a browser, and kills them too.
- `AGENT_FORCE_PRODUCTION=1` (testing only) makes every host count as production in the agent, the ctx fixture, the exported framework and the UI server. It can only make the guard stricter.
- The UI server reads `.env` too (dotenv), so `HOSTED`, `UI_USERS` and the provider keys can live there or in the systemd unit. The setup card writes to the same file.
- `RATE_LIMIT_FIRST=3 npm run api:local` (test hook) makes the first 3 `GET /products` answer 429 with `Retry-After: 1`, to watch the HTTP layer retry.
- `LOG_REQUESTS=1 npm run api:local` prints `<METHOD> <path><?query>` for every request the local API receives, to prove what the guard let through and which query parameters were sent.
- If `tsx` fails with "The service was stopped", macOS killed a quarantined esbuild binary (folder copied from a zip or download). Fix: `npm ci`.
- Restful Booker is a shared public server that resets its data; a random 404 there is not a code bug.
